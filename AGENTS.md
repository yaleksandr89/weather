# Weather: правила работы с репозиторием

## Область и архитектура

- Независимая Composer-библиотека `yaleksandr89/weather`, namespace `Yaleksandr\Weather\`, default branch `master`. Один root AGENTS.md; nested только при отдельном subtree contract.
- PHP `^8.4`, Guzzle `^8.0.1`, PSR-18/17/7 по composer.json. Проверять latest stable PHP официально до начала работ; support floor и совместимость tooling проверять раздельно. Не менять runtime dependencies или поддержку без решения владельца.
- `Weather::create()` — штатная сборка встроенных провайдеров через `ProviderFactory` и `DefaultHttpDependenciesFactory`; `Weather` принимает `CurrentWeatherProvider` для DI. Провайдеры используют PSR-18 client и PSR-17 factories; мапперы нормализуют ответы, value objects и `CurrentWeather` защищают инварианты. Сохранять framework-agnostic core, контракт текущей погоды по координатам и единицы измерения. Не добавлять прогнозы, поиск по городу, cache, retry, fallback, storage, logging или framework adapters без решения владельца.
- Сохранять фиксированные endpoints, HTTP/status/error semantics, валидацию координат и ответа, UTC timestamps, обработку неизвестных погодных кодов, запрошенные координаты и нормализацию единиц. WeatherAPI key передаётся в query по контракту сервиса; не выводить ключ, URI с ключом, исходные исключения транспорта с ключом или реальные приватные ответы в логи/отладку. Не ослаблять `SensitiveParameter`, `__debugInfo()` и существующее безопасное исключение транспорта WeatherAPI. Тесты только с синтетическими данными и mock HTTP, без live API.

## Стиль и документация

- PER Coding Style 3.1 + PSR-1, `@PER-CS` в PHP CS Fixer обеспечивает поддерживаемое подмножество; проверять отличия 3.1 вручную. PHP 8.4 позволяет `new Foo()->method()`; импортировать global classes при необходимости, strict types, PSR-4, native types, LF, 4 пробела, explicit visibility, английские identifiers. Не менять поведение ради стиля.
- Meaningful first-party PHP comments/PHPDoc: все строки RU: затем равнозначные EN:, machine-readable tags/type shapes не дублировать. Не придумывать комментарии к очевидному коду. PHPUnit identifiers English; human-facing TestDox по умолчанию RU.
- Русский канон: root README.md, `.github/CONTRIBUTING.md`, `.github/SECURITY.md`, тематические `docs/langs/ru/`; EN/ES/ZH/FR/DE в `docs/langs/<lang>/`. Сохранять примеры, предупреждения, навигацию, compact Mermaid во всех README; проверять code examples и ссылки по фактическому API, GitHub rendering отдельно. Обложка в `docs/assets/`, не менять без решения.
- LICENSE, SECURITY, FUNDING — owner-controlled. Согласованные tracked changes через Git, не через GitHub editor. Не публиковать реальные ключи, приватные данные или выдуманные live responses.

## Проверки, безопасность и Git

- Established: `composer test`, `composer analyse` (PHPStan max, PHP 8.4 floor, deprecation rules), `composer cs:check`, `composer cs:fix`, `composer check` (strict validate, audit, style, static, tests); `composer coverage` — локальная диагностика. Не добавлять Codecov. Библиотека без tracked lockfile; vendor/cache/coverage не коммитить. Тестировать meaningful behavior и failure paths обоих встроенных провайдеров, без тестов встроенного PHP ради процентов.
- До write: read-before-write, exact allowlist, risks/non-goals, security triage. Новые зависимости требуют official source, necessity, maintenance, compatibility/security и решения владельца. Не обновлять unrelated root constraints, не обходить platform/audit/style/static gates. При изменениях HTTP/credentials/validation/CI permissions — focused security review и meaningful tests. До runtime write проверить executable, effective user, ownership, side effects; никаких broad chmod/chown/delete, production или реальных секретов.
- Published package: до изменения public API, behavior, support получить owner decision о BC/migration/deprecation или breaking release. Не добавлять speculative shims. Remote `READ_ONLY_FOR_AI`; commit/push/PR/merge/settings/tag/Release/Packagist выполняет владелец; не rebase/reset/restore/clean/stash/force/delete без отдельного решения. После RW полный diff, `git diff --check`, staged `git diff --cached --check`, relevant actual gates, итоговый Git state. REVIEW ACCEPTED / NOT ACCEPTED; все findings одного полного review в одном corrective batch. PASS только по evidence.
- После финального merge проверить exact remote SHA и зелёный CI, затем владелец создаёт signed tag на тот же SHA; независимо проверить actual tag target/signature, Release и Packagist. Не выпускать промежуточный релиз из-за каждого PR или Settings.
